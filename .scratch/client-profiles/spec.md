# Спека: Профили клиентов (интервью, контекст, переключение, доступ)

Feature slug: `client-profiles` · Дата: 14.08.2026 · Источник: интервью autopilot (8 решений) + ADR-0001

## Problem Statement

Контент-завод обслуживает клиентов (компании-заказчики), но:

1. **Контекст клиента захардкожен в промптах генерации** — «Клиент: Robotec (промышленная робототехника, интегратор KUKA; тон: экспертно-деловой, ROI)» дословно в `SC/CT/ET/AU Build bridge prompt`. При нескольких клиентах бот не сможет генерировать контент «в контексте» нужной компании — любой профиль получит контекст Robotec.
2. **Нет механики заполнения профиля клиентом**: интервью по вопросам, ссылки на ресурсы компании, документы для погружения в контекст.
3. **Активный клиент глобальный** (`settings.active_client_id`) и **битый на live** (id 999 при отсутствующем клиенте) — per-чат переключения профилей нет.
4. **Доступ к боту — хардкод одного tg_user_id** в Whitelist; назначенных операторов нет.

## Solution

В боте появляется раздел **«Профиль»** (кнопка на старте и в меню): просмотр карточки активного профиля, создание нового профиля через интервью из 8 пропускаемых вопросов, выбор профиля из списка, редактирование (пере-опрос с предзаполнением + точечное добавление ссылок/документов), выход из профиля. Профиль собирает контекст компании: название, ниша, описание, ЦА, **ссылки на ресурсы**, **документы** (файлы PDF/DOCX/TXT — текст извлекается через hermes-bridge — или ссылки), тон, референсы. Активный профиль привязан к чату (по tg_user_id), и **все промпты генерации строятся из контекста активного профиля**, а не из хардкода. Владелец назначает операторов командой «добавить оператора <tg_id>»; назначенные получают доступ ко всему контент-заводу. Без активного профиля генерация недоступна (гейт с кнопкой «Профиль»).

## User Stories

1. Как оператор, я хочу видеть кнопку «Профиль» на стартовом экране и в главном меню, чтобы быстро попасть в раздел управления профилями.
2. Как оператор, я хочу видеть карточку активного профиля (название, ниша, описание, ЦА, тон, число ссылок и документов), чтобы понимать, в контексте какой компании идёт генерация.
3. Как оператор, я хочу создать новый профиль через интервью, чтобы бот узнал компанию без онбординга по URL.
4. Как оператор, я хочу пропускать любой вопрос интервью кнопкой «Пропустить», чтобы не блокировать создание профиля из-за отсутствующих данных.
5. Как оператор, я хочу вносить несколько ссылок на ресурсы компании по одной и завершать шаг кнопкой «Готово», чтобы собрать полный список ресурсов.
6. Как оператор, я хочу присылать документы (PDF/DOCX/TXT) в чат во время интервью и по кнопке «Добавить документ», чтобы контент-завод погрузился в материалы компании.
7. Как оператор, я хочу видеть подтверждение обработки документа (имя, размер текста), чтобы знать, что документ принят.
8. Как оператор, я хочу добавить документ ссылкой (Google Doc/Notion/файл на сайте), чтобы не присылать файл.
9. Как оператор, я хочу отменить интервью в любой момент («Отмена»), чтобы черновик не создавал мусорных профилей.
10. Как оператор, я хочу после завершения интервью увидеть карточку созданного профиля, чтобы проверить, что данные легли верно.
11. Как оператор, я хочу выбрать активный профиль из списка существующих, чтобы переключить контекст генерации.
12. Как оператор, я хочу выйти из профиля, чтобы бот не генерировал в чужом контексте, пока я не выберу профиль.
13. Как оператор, я хочу изменить профиль пере-опросом с предзаполненными ответами, чтобы исправить/дополнить данные.
14. Как оператор, я хочу точечно добавить ссылку или документ в существующий профиль без пере-опроса, чтобы быстро пополнить контекст.
15. Как оператор, я хочу, чтобы при отсутствии активного профиля генерация (цикл, URL→видео, шортсы, текстовый пост, ассеты) блокировалась с переходом в «Профиль», чтобы не получить контент без контекста.
16. Как оператор, я хочу, чтобы промпты аналитики/сценариев использовали контекст активного профиля (включая ссылки и документы), чтобы контент был релевантен именно этой компании.
17. Как владелец, я хочу назначать операторов командой «добавить оператора <tg_id>», чтобы дать доступ ко всему контент-заводу без правки кода.
18. Как владелец, я хочу видеть список операторов, чтобы контролировать доступ.
19. Как назначенный оператор, я хочу пользоваться всеми сценариями бота в своём чате со своим активным профилем, чтобы вести своих клиентов.
20. Как оператор, я хочу, чтобы у каждого чата был свой активный профиль, чтобы два оператора не «переключали» профиль друг друга.
21. Как оператор, я хочу, чтобы команда `onboard <url>` по-прежнему создавала профиль по сайту и делала его активным в моём чате, чтобы быстрый путь остался.
22. Как оператор, я хочу, чтобы legacy-команды `client <id>` / `clients` продолжали работать (выбор/список профилей), чтобы не ломать привычные сценарии.
23. Как оператор, я хочу видеть в статусе и на старте имя активного профиля из данных профиля (не из глобальных настроек), чтобы отображение не врало при нескольких чатах.
24. Как оператор, я хочу, чтобы при битом/отсутствующем активном профиле бот вёл в «Профиль» вместо тихого использования дефолта, чтобы контекст не был случайным.

## Implementation Decisions

### Модель данных (DDL напрямую на live factory.db — db-bridge DDL не выполняет)

- `ALTER TABLE clients ADD COLUMN description TEXT` — «что делает компания» (Q3).
- `ALTER TABLE clients ADD COLUMN context_links TEXT` — JSON-массив строк (Q5, ссылки на ресурсы).
- `ALTER TABLE clients ADD COLUMN context_docs TEXT` — JSON-массив `{"name": "...", "mime": "...", "text": "...", "chars": N}` (Q6, извлечённый текст/дайджест).
- `ALTER TABLE clients ADD COLUMN context_refs TEXT` — JSON-массив строк (Q8, конкуренты/референсы).
- `ALTER TABLE users ADD COLUMN active_client_id INTEGER` — per-чат активный профиль (NULL = нет).
- `ALTER TABLE sessions ADD COLUMN profile_draft TEXT` — черновик интервью (JSON).
- Сид: `INSERT OR IGNORE INTO users (tg_user_id, username, role) VALUES (941296693, 'owner', 'admin')`.

Схемы значений: Q4 (ЦА) → `clients.audience_json` как `{"raw": "<свободный текст>"}` (существующая OB-форма `{type, segments, decision_makers}` тоже остаётся валидной — отображение обрабатывает обе).

### Активный профиль: резолв per-чат (ADR-0001)

- Источник: `users.active_client_id` → fallback `settings.active_client_id` (legacy, поддерживается в синхроне при переключениях) → нет профиля (гейт).
- Все чтения `active_client_id` из `settings` (~11 Build-нод: ST/ST2/MU/IN/HL/DU/CM/OB/CL и др.) переводятся на паттерн:
  `SELECT u.active_client_id AS ac_id, (SELECT CAST(value AS INTEGER) FROM settings WHERE key='active_client_id') AS global_ac FROM users u WHERE u.tg_user_id = ?` (param из Parser; там, где Parser недоступен — добавить ссылку `$('Parser')`).
  JS-резолв в каждой ноде: `const ac = (u.ac_id ?? u.global_ac) ? Number(u.ac_id ?? u.global_ac) : 0;` — с валидацией существования клиента (битый id 999 → fallback: первый `status='active'` клиент или гейт).
- Записи: переключение/создание/выход пишут `users.active_client_id` (per-чат) и `settings.active_client_id` (совместимость) одним UPDATE-паттерном.

### Бот: новые команды и состояния (wf-tg-bot, база = live-экспорт 533 нод)

Parser (новые правила, слеш-формы обязательны — автокомплит Telegram):

- `profile` = `профиль` = `/profile` = `/профиль`; `profiles` = `профили` = `/profiles` = `/профили`
- `add_operator` = `добавить оператора <id>` (аргумент id); `operators` = `операторы` = `/operators`
- Документ: `if (item.message && item.message.document)` → `command='profile_doc'`, `args = {file_id, file_name, mime}` (приоритет над текстовым парсингом)
- Legacy: `client <id>` → `profile` с args.id; `clients` → `profiles`

Switch cmd — новые выходы: `profile`, `profiles`, `add_operator`, `operators`, `profile_doc` (правила +5; существующим веткам не ломать индексы — снапшот connections до мутаций).

Новые состояния `sessions.state`:

- `PROFILE_AWAIT` — интервью (новое/редактирование); шаг и ответы в `sessions.profile_draft` JSON: `{"mode":"new|edit","client_id":N|null,"step":1..8,"answers":{...},"links":[...],"docs":[...]}`
- `PROFILE_DOCS_SUBMITTING` — документ обрабатывается hermes-bridge (асинхронный шаг)

Ветка «Профиль» (PF):

- `profile` → PF Check (резолв активного клиента + строка clients) → PF Format (карточка, esc() везде) → TG profile с кнопками: `pf_new` (Создать профиль), `pf_list` (Выбрать профиль), `pf_edit` (Изменить), `pf_add_link` (Добавить ссылку), `pf_add_doc` (Добавить документ), `pf_exit` (Выйти из профиля), `cmd:menu` (📋 Меню)
- `pf_new` → PF Build start (INSERT draft, state=PROFILE_AWAIT, step=1) → вопрос 1 (кнопки «Пропустить» `pf_skip`, «Отмена» `cmd:cancel`)
- Каждый шаг: ответ (текст/URL/файл) → PF Parse answer (валидация по типу шага; URL-шаг — regex `^https?://`, файл-шаг — только в состоянии PROFILE_AWAIT при активном doc-шаге) → UPDATE draft → следующий вопрос или «Готово»/сохранение
- Шаг 5 (ссылки) и шаг 6 (документы) — мультизначные: кнопки «Готово» `pf_done` + «Пропустить»; ссылки копятся в draft.links; документы — в draft.docs через `profile_doc`
- Шаг 8 → PF Build save: INSERT (new) или UPDATE (edit) clients; запись per-чат active (users + settings); очистка draft; state=IDLE → PF Format (карточка) + кнопки
- `pf_exit` → UPDATE users.active_client_id=NULL (+settings fallback на первый active-клиент или NULL) → подтверждение + кнопка «Профиль»
- `pf_list`/`profiles` → SELECT id,name,domain FROM clients ORDER BY name → кнопки `pf_switch:{id}` (лимит 10; больше — текстовый список) → `pf_switch:{id}` → PF Build switch (валидация id) → запись per-чат → карточка
- `pf_edit` → draft {mode:'edit', client_id} → пере-опрос с предзаполнением (ответ по умолчанию = текущее значение; «Пропустить» = оставить)
- `pf_add_link` → состояние «жду ссылку» (draft mode=add_link, шаг-обработчик ссылок) → текст-URL → UPDATE clients.context_links (append) → подтверждение
- `pf_add_doc` → состояние «жду документ» (mode=add_doc) → файл/ссылка → append в context_docs
- `profile_doc` → HTTP hermes-bridge `/doc-text` (file_id, file_name, digest=true) → PF Doc parse (успех/ошибка; ошибка bridge → понятный текст, состояние возвращается на приём) → append draft.docs или clients.context_docs → ответ «Добавлено: <имя> (N симв.)»

Гейт активного профиля (входы генерации):

- start_cycle, url2video, shorts, text_post, asset, product, banner → перед цепочкой: PF Check gate (резолв активного клиента; нет → Format «Нет активного профиля — создай или выбери» + кнопка «Профиль»; есть → продолжение). Паттерн — как кредитные гейты (общий вход всех путей к платной цепочке).

### Контекст в промптах генерации (ядро «не путать контекст»)

- В каждой ветке с bridge-промптом (SC analyst, CT scriptwriter, ET analyst-ретрай, AU scriptwriter) вместо хардкода «Клиент: Robotec (…)» подставляется блок контекста активного профиля, построенный по единому паттерну: `CTX Build client` (SELECT строки clients по резолвленному id) → `CTX Format ctx` (сборка блока: название, ниша, описание, ЦА, тон, ссылки ≤5, документы-дайджесты ≤2000 симв. суммарно; esc() не нужен — текст уходит в JSON-промпт, не в TG) → промпт-билдер вставляет `ctx` в строку.
- OB (onboarding): после INSERT клиента — запись per-чат active (users+settings).

### hermes-bridge: новый эндпоинт `/doc-text`

- Метод POST, auth X-BRIDGE-TOKEN (как `/ask`); body `{"file_id": str, "file_name": str, "digest": bool}`.
- Логика: getFile(file_id) → download `https://api.telegram.org/file/bot<token>/<file_path>` (urllib, stdlib) в /tmp → извлечение текста по расширению/mime: `.txt/.md` raw; `.pdf` — pypdf; `.docx` — python-docx; прочее → `{"error": "unsupported type"}`.
- Зависимости pypdf/python-docx ставятся в `~/hermes-agent/.venv` **с явного согласия пользователя на деплое** (правило autopilot: пакеты на машине пользователя — только с разрешения). До установки — эндпоинт отвечает ошибкой «doc extraction not configured».
- Ответ: `{"name", "mime", "text", "chars"}`; text обрезан до 30k. `digest=true` → после извлечения LLM-дайджест (~800 симв.) через существующий механизм hermes CLI (маркерный контракт `<TEXT>...</TEXT>`, `--reasoning none`), при таймауте/ошибке LLM — fallback: обрезка текста до 2000 симв. В ответе: `{"text": "<дайджест или обрезка>", "chars": N, "digested": bool}`.
- Telegram с хоста: /etc/hosts маппинг api.telegram.org → fallback-IP уже есть на сервере (телеграм-фикс), urllib пройдёт.

### Доступ (Whitelist → users)

- Цепочка: tg-trigger → HTTP db-bridge `SELECT role FROM users WHERE tg_user_id=?` (param из item) → Code Access check (нет строки → `return []`; роль `admin`/`operator` → pass; прочее → `[]`) → Parser. Хардкод `TG = 941296693` в Whitelist/Parser убирается из access-логики (в Parser остаётся только для отображения/легаси, если нужно).
- `add_operator <tg_id>`: ролевой гейт (только `admin`) → INSERT OR IGNORE users (role='operator', username='') → подтверждение. `operators`: SELECT tg_user_id, username, role → список.
- Ошибка доступа для не-whitelisted: поток обрывается молча (как сейчас `return []`).

### Команды Telegram (setMyCommands)

- tg-commands-31.json → расширить: `profile` («Профиль: создать, выбрать, изменить, контекст»), `profiles` («Список профилей»), `add_operator` («Добавить оператора <tg_id> (admin)»), `operators` («Список операторов (admin)») → новый файл tg-commands-35.json + register-скрипт (паттерн register-tg-commands-31.sh).

## Testing Decisions

- **Структурные (всегда, 0 кредитов)**: `validate_workflow.py` (BFS от tg-trigger, node --check всех jsCode, дубли имён/id — ожидание 0 issues на 533+ нод), `lint-workflow-json.py` (esc-покрытие новых TG-нод, callback_data без `=`-префикса, статичные тексты с `_`), `extract-tg-ux-map.py` (новые кнопки pf_*, [BROKEN]/[NOROUTE] — сверять с Parser, помня о ложных NOROUTE на menu_*/dur_*).
- **Поведенческие (симуляция Code-нод)**: `sim-code-node-both.py` / `sim-code-node.py` / `sim-code-node-json.py` — для Parser (новые команды, document-ветка), PF Check/Format/Build (резолв, draft JSON, сохранение), CTX Build/Format (сборка блока из клиентской строки, обрезки), gate-нод (нет профиля → сообщение), Access check (роль admin/operator/нет строки).
- **Bridge `/doc-text`**: локальный smoke (auth 401 без токена; bad request 400; unsupported type 422/400; unit-тест extract_text на сэмплах txt/pdf/docx в /tmp); E2E с реальным TG-документом — только в деплой-гейте с согласия (это трафик Telegram, не платные API).
- **Live 0-кред**: webhook-probe с fake from.id (не в users → 200, тишина; owner → проходит); sqlite-проверки (users.active_client_id, clients контекст-колонки, sessions.profile_draft); `node --check` jsCode; сверка числа нод после каждого тикета.
- **Кредиты**: фича не требует платных вызовов; все тесты «до точки списания»; мониторинг, что гейт профиля стоит раньше кредитных гейтов (BFS-проверка путей).

## Out of Scope

- Удаление профилей (только «выйти»; физическое удаление — вне фичи) и удаление операторов (правка БД вручную).
- Редактирование списка вопросов интервью владельцем (список фиксирован в воркфлоу).
- Парсинг вложений, кроме документов (фото/видео/аудио) — отклоняются с подсказкой.
- Возобновление прерванного интервью («Отмена» = черновик выбрасывается).
- Пагинация списка профилей (>10 — текстовый список без кнопок).
- Per-профильные настройки публикации (selected_platforms остаётся в сессии), аватары/голоса профиля (legacy settings preferred_*).
- Шифрование содержимого документов (ограничение размера 30k/документ).
- Автоматический онбординг из документов (текст сохраняется, но LLM-структуризация профиля из документов — отдельная фича).

## Further Notes

- База для реворка — live-экспорт wf-tg-bot 533 нод (`.scratch/review-full-14aug/fixes/wf-tg-bot.json` синхронизирован с live); репо `workflows/wf-tg-bot.json` тоже 533 нод.
- Live `settings.active_client_id = 999` (битый) — фича чинит это резолвом с валидацией + fallback.

- Секретов в фиче нет; файлы документов не хранятся (только извлечённый текст в БД).

# Волна 2: закрытие Out of Scope (15.08, autopilot semi — интервью 6 решений)

## Problem Statement

Из волны 1 в Out of Scope ушли 5 механик, которые заказчик хочет видеть в продукте: удаление профилей и операторов, редактирование списка вопросов интервью, приём фото (OCR) в контекст профиля, возобновление прерванного интервью, per-профильные настройки публикации.

## User Stories

1. Как оператор, я хочу удалить профиль с подтверждением, чтобы убрать неактуального клиента без потери истории (мягкое удаление).
2. Как владелец, я хочу удалить оператора командой с подтверждением, чтобы отозвать доступ; себя удалить нельзя.
3. Как владелец, я хочу редактировать вопросы интервью («вопрос N <текст>») и сбрасывать к дефолту, чтобы адаптировать интервью под клиентов.
4. Как оператор, я хочу приложить фото компании к профилю, чтобы текст с картинки (OCR) попал в контекст генерации.
5. Как оператор, я хочу продолжить прерванное интервью с того же шага (или начать заново), чтобы не вводить ответы повторно.
6. Как оператор, я хочу задать профилю дефолтные платформы публикации, чтобы шаг публикации открывался с предвыбранными платформами.

## Implementation Decisions

- **Удаление профиля — мягкое**: `UPDATE clients SET status='deleted'` (данные остаются; резолв/списки фильтруют `status='active'`); кнопка «🗑 Удалить» в карточке → «Точно удалить?» (pf_del → pf_del_yes/pf_del_no); если удаляемый профиль активен в чате → `users.active_client_id=NULL` + settings-синхрон (первый active).
- **Удаление оператора**: команда «удалить оператора <id>» (роль admin отправителя; id ≠ свой; `DELETE FROM users WHERE tg_user_id=? AND role='operator'` → подтверждение; владелец → «нельзя»). Операторы-строки в списке показывают роль.
- **Фото → OCR**: `message.photo` → `profile_photo` (file_id наибольшего размера); hermes-bridge `/img-text` (download фото → Hermes-зрение: «извлеки весь текст, верни строго в TEXT-маркерах», fallback ошибка); результат в `context_docs` как {name, mime:'image/…', text, chars}. Видео (`message.video`) → отклонение «Видео пока не поддерживаем — пришли PDF/DOCX/TXT/фото или ссылку».
- **Вопросы интервью**: `settings.profile_questions` (JSON-массив, сид дефолтных 8); PFN Qlist читает вопросы из settings (fallback — дефолт); команды: «вопросы» (список), «вопрос N <текст>» (замена, 1..8, admin), «вопросы сброс» (дефолт).
- **Возобновление интервью**: pf_new → PFN Check: если state=PROFILE_AWAIT и draft есть → «Нашёл черновик: продолжить с шага N?» (pf_resume / pf_restart / Отмена); pf_resume → Qlist с шага N; pf_restart → новый draft. Карточка профиля: кнопка «📝 Продолжить интервью» при наличии draft.
- **Per-профильные платформы**: `clients.publish_platforms TEXT` (JSON-массив); редактирование — кнопка «📱 Платформы» в карточке (чекбокс-переключатели, как stage4) или команда «платформы <список>» (admin); шаг публикации (stage4) инициализирует `selected_platforms` из профиля (предвыбранные, можно менять).
- Схема v2: `clients += publish_platforms`; `settings += profile_questions` (сид).

## Testing Decisions

- Структурные: validate/lint/node --check/extract-tg-ux-map (как волна 1); sim: PFN Qlist с кастомными вопросами; PFN Check resume; PD Parse фото; stage4 pre-select; PSW/PX-подобные ветки удаления.
- Bridge `/img-text`: локальные тесты с mock (auth 401, bad request, отсутствие vision-обработки → ошибка); живой OCR-тест — в деплой-гейте (согласие).
- 0 платных вызовов; live-тесты read-only + TG-трафик по согласованию.

## Out of Scope (остаётся)

- Жёсткое удаление данных (восстановление мягко удалённых), массовое редактирование вопросов (только по одному), видео-транскрипция, per-профильные голоса/аватары, шифрование документов.

# Волна 3: довести систему до зелёного (15.08, autopilot semi — интервью 4 решения)

## Problem Statement

При live-проверке деплоя волн 1+2 вскрылись латентные баги всей системы: 24 boolean-Switch-ноды с неверным типом оператора (генерация была мертва), 40 TG-нод без credentials (ветки URL→видео/длительность/дубли не слали сообщения). Пользователь требует: все 24 не-архивных воркфлоу — рабочие и без ошибок; платные тесты проводит сам (моя граница — «до точки списания»).

## User Stories

1. Как оператор, я хочу, чтобы любой сценарий бота (цикл, URL→видео, шортсы, профиль, публикация) реально отвечал в чате, без «Node does not have credentials» и «Wrong type» ошибок.
2. Как владелец, я хочу видеть отчёт о работоспособности всех 24 воркфлоу (структура + runtime + бесплатные smoke-пути).
3. Как владелец, я хочу, чтобы найденные при аудите проблемы были исправлены до зелёного статуса.

## Implementation Decisions

- **Т22 — TG-credentials**: всем TG-нодам без credentials проставить `{"telegramApi": {"id": "10000000-0000-4000-8000-000000000004", "name": "telegram"}}` (эталон — рабочие ноды); просканировать и другие credential-типы (httpRequest с auth и пр.); validate/lint → передеплой.
- **Т23 — ретест start_cycle + закрытие live-чек-листа волн 1+2**: пробы с secret-token (владелец/фейки), интервью до сохранения, документ TXT, фото OCR, переключение/удаление, вопросы, платформы, гейт, CTX в промптах. 0 кредитов.
- **Т24 — аудит 24 воркфлоу**: структурные валидаторы (validate/lint/BFS/node --check/typeVersion против n8n 2.34.4: telegram v1.2, switch v3.4, http 4.5...), свежие исполнения без error, бесплатные smoke-пути; отчёт-таблица по каждому.
- **Т25 — фиксы по аудиту** (по воркфлоу, субагентами).
- **Т26 — синк репо + коммит + финальный отчёт** (после зелёного деплоя).
- Граница кредитов: НЕ вызывать платные эндпоинты (creatify генерации, scrapecreators); тесты «до точки списания».

## Testing Decisions

- Live: webhook-пробы с детерминированным secret-token ({workflowId}_{nodeId}), фейковые id для отказных веток, реальные сообщения владельцу (согласовано), анализ execution_data/execution_entity (status, lastNodeExecuted, ошибки).
- Структурно: те же валидаторы скилла + сверка typeVersion новых нод с эталоном n8n 2.34.4.
- Кредиты: 0.

## Out of Scope

- Платные smoke-тесты (генерация видео, публикация) — проводит пользователь.
- Изменение продуктовой логики вне найденных ошибок.
