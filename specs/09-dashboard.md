# Спека 09 — Веб-дашборд (Next.js)

**Фаза:** P2 · **Статус:** к реализации после закрытия клиента

> TG-бот полностью покрывает MVP и операционные задачи. Дашборд — это
> **клиентский интерфейс самообслуживания**: чтобы отдать продукт клиенту «как
> SaaS», не заставляя его работать в чужом Telegram. Разворачивается только если
> первый клиент закрылся и нужен «фасад».

## 1. Цель

Дать клиенту (и оператору) графический интерфейс для:
- просмотра сгенерированных роликов и постов;
- просмотра метрик по своим публикациям (из спеки 07);
- управления очередью/расписанием публикаций;
- управления профилем клиента (ниша, тон, лимиты, конкуренты);
- онбординга новых клиентов (P2 мульти-тенантность).

> Дашборд **не заменяет** TG-бот — они сосуществуют. Бот для оператора/алертов,
> дашборд для клиента/самообслуживания. Оба читают/пишут одну БД.

## 2. Стек

| Слой | Технология | Почему |
|------|------------|--------|
| Frontend | **Next.js 14+ (App Router)** | SSR, RSC, простое развертывание, один репозиторий |
| Стили | Tailwind CSS | скорость, дефолтный хороший UI |
| Backend (read) | Next.js Route Handlers / Server Components → SQLite | без отдельного API-сервиса |
| Backend (write/actions) | Next.js Server Actions + Zod-валидация | типобезопасно, без REST-церемоний |
| БД | тот же SQLite (`/var/data/factory.db`) | read-only соединение из Next |
| Авторизация | простой session-cookie + пароль (мульти-пользователи P2) | без OAuth на первом этапе |
| Контейнер | отдельный сервис в `docker-compose.yml`, порт 3000 | рядом с n8n/Hermes |

**Почему не отдельный FastAPI/Express:** Next позволяет держать фронт и
read-API в одном процессе → меньше движущихся частей, проще деплой, достаточно
для витрины. При росте — вынести read-API в отдельный сервис легко.

## 3. Страницы (карта сайта)

```
/                       → Dashboard (обзор: сегодня, кредиты, последние ролики)
/login                  → вход (пароль / session)
/onboard                → форма «добавить клиента по URL» (визуальный аналог /onboard)
/clients/[id]           → профиль клиента (ниша, тон, соцсети, конкуренты)
/content
  /videos               → лента сгенерированных видео (превью, статус, метрики)
  /posts                → лента текст-постов
  /new                  → ручной запуск цикла (тема/сценарий/генерация)
/schedule               → очередь и расписание публикаций (календарь)
/analytics              → метрики по своим роликам (из спеки 07)
/settings               → лимиты, аватары/голоса creatify, cron-время
/logs                   → журнал событий (для админа, с фильтром)
```

## 4. Ключевые экраны (детализация)

### 4.1 Dashboard (`/`)
- Карточки: **видео сегодня / за месяц**, **остаток кредитов creatify**,
  **запланированных постов**, **средние метрики за 14 дней**.
- Лента «последние 6 роликов» с превью и мини-метриками.
- Бейдж режима (manual/auto) и активного клиента.

### 4.2 Лента видео (`/content/videos`)
- Сетка карточек: превью (играет по hover), длительность, статус
  (done/failed/published), платформы куда ушло, просмотры/лайки.
- Фильтры: по дате, статусу, клиенту (P2), платформе.
- Клик → модалка с деталями: сценарий, исходный тренд, JSON-запрос creatify,
  метрики по каждой соцсети.
- Действия (для админа): «перегенерировать», «удалить», «скачать MP4».

### 4.3 Запуск цикла (`/content/new`)
- Форма: выбрать клиента → кнопка «Запустить аналитику».
- Показывает топ-кандидатов → выбор темы → утверждение сценария →
  предпросмотр JSON → «Сгенерировать».
- Это **визуальный аналог ручного TG-цикла**, для тех, кто не любит чат-боты.

### 4.4 Расписание (`/schedule`)
- Календарь (неделя/месяц): карточки запланированных постов на таймлайне.
- Drag-and-drop переноса времени (опц., P2.1) → Server Action обновляет `post_at`.
- Индикатор статуса каждого поста (pending/published/error).

### 4.5 Аналитика (`/analytics`) — данные из спеки 07
- Графики (recharts/visx): просмотры/лайки/охват во времени.
- Топ-3 формата/темы (что зашло).
- Сравнение платформ (где лучше всего заходят Reels клиента).

### 4.6 Онбординг (`/onboard`)
- Поле ввода URL → прогресс «анализирую…» → карточка профиля с
  кнопкой «Принять» (повторяет TG-флоу из спеки 08, но в UI).

### 4.7 Настройки (`/settings`)
- Поля: ниша, тон, аудиторрия (редактируемые из профиля клиента).
- Селекты: аватары/голоса creatify (из кеша).
- Числа: daily/monthly video limit, credit_floor, cron time.
- Список конкурентов (добавить/удалить).

## 5. Связь с бэкендом (n8n/Hermes)

Дашборд **не дёргает** n8n/Hermes напрямую для каждого действия — это создало
бы вторую точку управления и рассинхрон. Вместо этого:

- **Read** — напрямую из SQLite (Next Server Components, read-only соединение).
- **Write/Actions** — два пути:
  1. Простые правки (настройки, профиль) → Server Action → SQLite напрямую.
  2. **Запуск цикла / генерация / публикация** → Server Action дёргает **тот же**
     `POST /internal/start-cycle` на Hermes, что и TG-бот. Единая шина →
     одинаковая логика, один источник правды.

```
[TG-бот] ──────┐
               ├──► POST :8000/internal/* ──► Hermes ──► n8n ──► APIs
[Дашборд] ─────┘
```

> Это исключает дублирование: что бы ни делал пользователь (кнопка в TG или
> клик в дашборде) — летит в один эндпоинт Hermes.

## 6. Авторизация

- **MVP дашборда (P2.0):** один общий пароль на `/login` (из env
  `DASHBOARD_PASSWORD`), session-cookie (httpOnly, SameSite=strict), срок 7 дней.
- **P2.1 (мульти-пользователи):** таблица `dashboard_users` (login, password_hash,
  client_id, role). Каждый клиент видит только свой контент (`WHERE client_id = ?`).
- **P2.2:** OAuth через Google (для клиентов, кто не хочет ещё один пароль).

## 7. Безопасность

- Дашборд **за тем же HTTPS reverse-proxy**, публичный маршрут `/` требует
  авторизацию (middleware).
- Read-соединение к SQLite — **read-only** (`PRAGMA query_only=1` или отдельный
  read-user через SQL-функции). Write — только через Server Actions с валидацией.
- CSP-заголовки, запрет inline-script (Next это умеет из коробки).
- Никаких API-ключей creatify/scrapecreators/postmypost в дашборде — они
  остаются в n8n Credentials. Дашборд видит только «остаток кредитов» (значение
  из `settings`, обновляемое n8n).
- Рейт-лимит на `/login` (5 попыток / минуту) — от брутфорса.

## 8. Контейнеризация

Добавить в `docker-compose.yml`:
```yaml
dashboard:
  build: ./dashboard
  ports:
    - "3000:3000"           # только localhost или за reverse-proxy
  environment:
    - DATABASE_PATH=/var/data/factory.db
    - HERMES_INTERNAL_URL=http://hermes:8000
    - DASHBOARD_PASSWORD=${DASHBOARD_PASSWORD}
  volumes:
    - ./data:/var/data:ro   # read-only к БД для read-запросов
    - ./media:/var/media:ro # read-only к медиа для превью
  depends_on: [hermes]
```

> Write в БД из дашборда — через тот же файл; read-only монтирование
> предотвращает случайные записи из Server Components. Server Actions могут
> открывать отдельное read-write соединение по тому же пути (на одном хосте
> SQLite-у это безопасно с WAL).

## 9. Производительность

- RSC + SQLite на одном хосте → запросы ~миллисекунды.
- Кеширование: Next `unstable_cache` / `revalidateTag` для тяжёлых агрегаций
  (метрики по всем постам) с инвалидацией по событию (webhook из n8n
  «новая публикация» → `revalidateTag('posts')`).
- Превью видео — стримятся из `/var/media` через reverse-proxy (как в спеке 05).

## 10. Критерии готовности (P2)

1. `/login` пускает по паролю, незалогиненный `401`.
2. Dashboard показывает живые данные (не моки) из SQLite.
3. Лента видео отображает превью и статусы реальных генераций.
4. `/content/new` запускает полный цикл (через Hermes, как TG).
5. `/onboard` повторяет TG-флоу и пишет в ту же таблицу `clients`.
6. `/analytics` строит графики по данным из `post_metrics` (после спеки 07).
7. Авторизация и SSRF-защита работают (онбординг отклоняет приватные URL).
8. Разворачивается одной командой `docker compose up` рядом с остальным стеком.

## 11. Этапы внутри P2

- **P2.0 — single-tenant MVP:** пароль, один клиент, базовые страницы
  (dashboard/videos/posts/new/onboard/settings/logs). Без аналитики.
- **P2.1 — аналитика:** подключение данных из спеки 07 (post_metrics), графики.
- **P2.2 — мульти-тенантность:** пользователи с client_id, изоляция контента.
- **P2.3 — расписание drag-and-drop + OAuth.**
